LUCK-CAYS
Online Casino — Security-First Shell / Framework Build Specification
Agent-ready engineering brief • September 2026
Goal: build the production-quality website shell/framework for Luck-Cays before connecting real-money gambling, payment processing, or live casino operations. The framework must be modular so approved regulated services can be connected later without rebuilding the core application.
CRITICAL: Do not enable real-money deposits, wagers, withdrawals, or prizes until the operators have confirmed the applicable gambling licenses, jurisdictions, age/KYC/AML requirements, payment-provider approvals, responsible-gaming requirements, and technical obligations with qualified legal/compliance professionals.
1. Core Principles
•	Security is the first engineering requirement, not a later feature.
•	Authentication and identity are centralized.
•	The wallet is a financial ledger, not a simple balance number.
•	Payments use provider adapters and tokenization; never store raw card data.
•	Games are server-authoritative when real money is eventually introduced.
•	Sensitive actions are auditable.
•	Jurisdiction and eligibility restrictions are enforced centrally.
•	The site is responsive, accessible, modular, and testable.
•	Development uses fake/test money only.
2. Payment / Regulatory Reality
Do not assume ordinary card processors or PayPal can simply be connected to an online casino. Provider policies and jurisdictional rules can prohibit or restrict gambling. Stripe's current restricted-business documentation lists internet gambling/casino activity among prohibited businesses, while PayPal states that approved gambling merchants may use PayPal in certain jurisdictions subject to approval and restrictions. The Gaming Board for The Bahamas publishes AML/CFT/CPF materials. Therefore, Luck-Cays must use an approved provider for its actual business model and jurisdictions.
Architecture rule: build a PaymentProvider interface and a fake/sandbox provider now. Do not hard-code Stripe, PayPal, or any other provider as though approval is guaranteed.
3. Recommended Architecture
•	Frontend: React + TypeScript + Vite/Next.js, or preserve the team's existing framework.
•	Backend: Node.js + TypeScript with a structured API framework.
•	Database: PostgreSQL or MySQL with migrations, foreign keys, transactions, and least-privilege users.
•	Cache/rate limiting: Redis or equivalent managed service.
•	Authentication: managed identity provider or carefully implemented server-side authentication.
•	Private object storage for documents if legally required; short-lived signed URLs.
•	Production secrets stored in a secrets manager/vault.
•	Structured logging, metrics, error tracking, uptime monitoring, and security alerts.
•	CI/CD with tests, linting, dependency scanning, and secret scanning.
4. Security — Highest Priority
•	Passwords: Argon2id or another modern adaptive password hash; never plaintext or reversible passwords.
•	Sessions: secure HttpOnly/SameSite cookies, session rotation after login and privilege changes, session/device management.
•	MFA: authenticator-app TOTP and/or WebAuthn/passkeys; require step-up authentication for sensitive actions.
•	CSRF: SameSite protections plus CSRF defenses for state-changing browser requests.
•	XSS: framework escaping, validation, safe output encoding, strict CSP, and no unsafe HTML injection.
•	SQL injection: parameterized queries/ORM only.
•	Rate limiting: login, signup, reset, MFA, deposits, withdrawals, promo redemption, support abuse, and admin endpoints.
•	Security headers: HSTS, CSP, frame-ancestors, Referrer-Policy, Permissions-Policy, MIME sniffing protection.
•	Secrets: never commit .env files, API keys, DB passwords, JWT secrets, encryption keys, or provider credentials.
•	Encryption: TLS everywhere; encrypt sensitive data at rest where appropriate; separate keys from ciphertext.
•	Audit logs: security, account, payment, wallet, compliance, and admin events with timestamp, actor, result, and correlation ID.
•	Admin: separate admin auth, mandatory MFA, least privilege, short sessions, and complete audit trails.
•	Dependencies: lock versions, scan vulnerabilities, remove unused packages, patch critical issues.
•	Backups: encrypted backups plus tested restores and a documented retention policy.
5. Preventing Duplicate / Multi-Account Abuse
Email and phone uniqueness are useful, but they should NOT be the entire anti-multi-account system. Use several identity and risk signals. Some are hard uniqueness constraints; others should trigger review rather than automatically banning legitimate people.
•	Email: normalize, verify, and enforce a unique database constraint.
•	Phone: normalize to E.164, verify, and enforce uniqueness where appropriate.
•	KYC identity: after required identity verification, keep a protected unique identity reference/key. Do not expose raw government-ID numbers in normal tables.
•	Age verification: verify rather than merely trusting a typed birth date when required.
•	Payment instruments: use provider tokens/references or permitted provider fingerprints; never store raw PAN/CVV.
•	Account-linking service: connect accounts to verified identifiers, payment references, devices, sessions, and other permitted signals.
•	Risk signals: device/session reputation, IP/ASN, geolocation, velocity, repeated failed attempts, and behavioral anomalies.
•	Do not permanently block solely because two people share an IP/device; households, schools, workplaces, and public networks can share them.
•	Withdrawal destination checks can identify suspicious reuse where lawful and appropriate.
•	Suspicious relationships should enter a controlled manual-review queue with evidence and reason codes.
6. Card / PayPal Payment Architecture
Use hosted payment fields or provider tokenization from an approved provider. Luck-Cays should receive a provider token/reference rather than raw card data. Never store card numbers or CVV/CVC.
•	PaymentProvider.createDepositIntent()
•	PaymentProvider.confirmDeposit()
•	PaymentProvider.getTransactionStatus()
•	PaymentProvider.createWithdrawalRequest()
•	PaymentProvider.verifyWebhook()
•	Use signed webhook verification.
•	Make webhook processing idempotent and resistant to replay.
•	Store provider transaction IDs and statuses, not unnecessary payment credentials.
•	Reconcile external provider records against the internal ledger.
•	Development provider = fake/sandbox implementation only.
7. Wallet / Money Ledger
Never implement money as `users.balance = users.balance + amount`.
•	wallets: wallet metadata/currency.
•	ledger_transactions: immutable financial transaction header.
•	ledger_entries: debit/credit entries.
•	payment_transactions: external provider references/statuses.
•	withdrawal_requests: withdrawal workflow/status.
•	Separate cash and promotional/bonus balances.
•	Every financial operation uses a database transaction.
•	Use idempotency keys so retries cannot duplicate deposits.
•	The server is authoritative; never trust a frontend balance.
•	Use integer minor units or exact decimal arithmetic, never floating-point money calculations.
•	Do not delete financial ledger records; correct mistakes with compensating transactions.

25. Build Phases
Phase 0 — Repository inspection: Inspect existing files, framework, database, routes, auth, environment, and components. Preserve working functionality.

Phase 4 — Wallet: Fake-money ledger, transaction history, idempotency, reconciliation architecture, and payment-provider interfaces.
Phase 5 — Casino shell: Game lobby, cards, categories, search, favorites, recent games, launch shell, promotions, VIP, jackpots.
Phase 6 — Compliance shell: KYC status, responsible gaming, self-exclusion/cooling-off, jurisdiction controls, review states.
Phase 7 — Admin: RBAC, users, security events, configuration, feature flags, content, games, reconciliation, audit.
Phase 8 — Testing: Unit, integration, E2E, security, race-condition, authorization, webhook, and responsive tests.
Phase 9 — Production hardening: Threat model, secret audit, dependency audit, monitoring, backups/restore test, penetration test, incident-response plan, legal/compliance review.
